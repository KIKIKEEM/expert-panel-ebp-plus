# 근거 기반 전문가 패널 v3.3

$ARGUMENTS

주어진 주제에 대해 **관련 학문 분야의 근거를 먼저 탐색**한 후, 해당 근거에 기반한 전문가 패널 토론을 진행합니다.

> 설계 원칙: "전문가가 이렇다고 해서 무조건 따르지 않는다. 근거 없는 전문가 조언은 안 하느니만 못할 수 있다." (EBP - Evidence-Based Practice)

---

## Dispatch

`$ARGUMENTS`를 파싱하여 실행 흐름을 결정한다:

| 인자 패턴 | 흐름 | 설명 |
|-----------|------|------|
| `[주제]` | Full Flow (0→7단계) | 전체 프로세스 |
| `[주제] --quick` | Quick Flow (0→4→5→6→7) | 학문 지도(1)·근거 지형(2)·깊은 제약(3) 생략, Mirror(0)만 유지, `▶ [0/4]`부터 시작 |
| `[주제] --experts [전문가1, ...]` | Full Flow + 전문가 오버라이드 | 4단계에서 사용자 지정 전문가 사용 |
| (빈 입력) | 주제 요청 | "어떤 주제에 대해 전문가 패널을 소환할까요?" |

**Gate 통과는 반드시 눈에 보이는 한 줄로 출력한다.** 각 단계 끝에서 다음 형식으로 자기검증 결과를 표기 — 내부 판단만으로 통과 처리하지 않는다:
```
✓ Gate [N] 통과 — {통과 근거를 수치/사실로: 예) 학문분야 3개 식별, 원문 링크 2개 확인}
```
미충족이면 `✗ Gate [N] 미충족 — {부족한 항목}` 을 출력하고 해당 단계의 fallback을 수행한 뒤 다시 검사한다.

## 6축 매핑 (Harness Engineering)

| 축 | 단계에서 적용 | 메커니즘 |
|----|--------------|----------|
| **구조** | 전 단계 | 8단계(0-7) layered phase + ✓ Gate + 미달 시 fallback |
| **맥락** | **0단계 + 3단계 (분할 게이트)** | 0단계: Mirror + 현재 상황 / 3단계: 자원·제약·측정기준 |
| **계획** | 1-2단계 | 학문 지도 → 근거 지형 (사용자 맥락에 좁혀진 탐색) |
| **실행** | 4-6단계 | 근거 태그 강제, Core/Peripheral 분리, MVE 설계 |
| **검증** | 게이트 + 종료 체크리스트 | 출력형 ✓/✗ Gate(수치 근거 명시) + Hard Rules + Checklist Before Stopping |
| **개선** | 7단계 + PBE Loop | 옵시디언 저장 → 후속 회고에서 N-of-1 축적 |

## 실행 단계

### ▶ [0/7] Goal Mirror & 현재 상황 (Pre-flight User Gate)

근거 탐색 전, 사용자가 풀려는 진짜 문제와 현재 위치를 잡는다. **분할 게이트의 앞쪽** — 1-2단계 학문 지도/근거 탐색이 사용자 맥락에서 빗나가지 않도록 좁혀준다.

수행 항목:
1. **텍스트 Mirror** — 주제를 한 문장으로 되돌려준다. 형식:
   > "이해한 바로는 [주제]에 대해 [어떤 결정/판단]이 필요하신 것 같습니다. 범위 밖: [무엇은 다루지 않음]. 맞나요?"
2. 사용자가 정정하면 반영 후 다시 mirror
3. **`AskUserQuestion` 1개** — 현재 상황(상태)만 빠르게 확인 (제약·도구는 3단계로 미룸)

표준 질문 패턴 (현재 상황 1개만):
```
AskUserQuestion(
  question: "현재 [주제]와 관련해 어떤 상황에 가장 가까우세요?",
  header: "현재 상황",
  options: [
    { label: "[옵션 A]", description: "주제 특성에 맞는 시나리오" },
    { label: "[옵션 B]", description: "주제 특성에 맞는 시나리오" },
    { label: "[옵션 C]", description: "주제 특성에 맞는 시나리오" }
  ]
)
```

이 단계의 핵심: 1-2단계가 **사용자와 무관한 학문 일반론**으로 흐르지 않게 좁혀주는 것. 깊은 제약·도구·측정기준은 3단계에서 수집(근거를 본 후가 더 의미 있는 답이 나옴).

> ✓ Gate 0: Mirror 합의 + 현재 상황 1개 응답 수집 완료. 미충족 시 → Mirror 재시도 또는 옵션 재구성.

### ▶ [1/7] 학문 지도 그리기 (Science Mapping)

`$ARGUMENTS`에서 주제를 파악한 후, **관련 학문 분야를 먼저 식별**한다.

수행 항목:
- 주제와 관련된 학문 분야(XX Science, XX Psychology, XX Studies 등) **2-4개** 식별
- 각 분야에서 이 주제에 대해 어떤 종류의 연구가 축적되어 있는지 개요 제시
- 가장 관련성 높은 1-2개 분야를 **주 근거원(primary evidence source)**으로 선택

출력 형식:
```markdown
## 학문 지도

| 분야 | 관련성 | 핵심 연구 주제 | 근거 풍부도 |
|-----|--------|---------------|-----------|
| [분야명] | 높음/중간 | [이 분야에서 다루는 관련 주제] | 풍부/보통/희소 |

**주 근거원**: [선택한 1-2개 분야와 선택 이유]
```

> ✓ Gate 1: 학문 분야 2개 이상 식별 + 주 근거원 선택 완료. 미충족 시 → 인접 학문 분야로 확대 탐색.

---

### ▶ [2/7] 근거 지형 탐색 (Evidence Landscape)

주 근거원 분야에서 **핵심 발견들을 정리**한다. **WebSearch를 사용하여** 메타분석, 체계적 리뷰를 우선 탐색한다.

수행 항목:
- **WebSearch**로 해당 분야의 메타분석, 체계적 리뷰, 주요 연구를 탐색 (최근 10년 이내 우선)
- **WebFetch로 원문 확인** — `[Strong]`/`[Moderate]` 태그를 붙이려는 발견은 검색 스니펫만으로 확정하지 말고, 최소 1개 이상 URL을 WebFetch로 열어 저자·연도·표본크기·핵심 수치가 스니펫과 일치하는지 확인한다. 열어볼 수 없거나 스니펫만으로 판단한 경우 태그를 한 단계 낮추거나(`[Emerging]`) `(원문 미확인)`을 병기한다
- WebSearch/WebFetch 사용 불가 시 내부 지식으로 진행하되, 모든 발견에 `[Internal Knowledge]` 태그 부착
- **설명적 근거 (Descriptive)**: 이 현상이 어떻게 작동하는가? 무엇이 관찰되는가?
- **처방적 근거 (Prescriptive)**: 어떻게 하면 더 효과적인가? 무엇이 검증되었는가?
- 각 발견에 **근거 수준** 태그와 **원문 URL**을 함께 부여 (URL 없이는 `[Strong]`/`[Moderate]` 부여 금지 — 자세한 내용은 Hard Rules 참조)

근거 수준 체계 (`references/evidence-framework.md` 참조):
- **[Strong]**: 메타분석, 체계적 리뷰, 복수의 재현된 실험
- **[Moderate]**: 복수의 RCT 또는 대규모 관찰 연구
- **[Emerging]**: 단일 연구, 예비 결과, 파일럿 스터디
- **[Expert]**: 전문가 합의, 임상 경험 기반 (근거 약함 — 주의 필요)
- **[Contested]**: 상반된 연구 결과가 존재

출력 형식:
```markdown
## 근거 지형

### 설명적 발견 (이렇게 작동한다)
- [Strong] 발견 내용 — 저자 (연도), [원문 링크](URL)
- [Moderate] 발견 내용 — 저자 (연도), [원문 링크](URL)

### 처방적 발견 (이렇게 하면 효과적이다)
- [Strong] 발견 내용 — 저자 (연도), [원문 링크](URL)
- [Emerging] 발견 내용 — 저자 (연도), [원문 링크](URL) 또는 (원문 미확인)

### Gottman 경고 (근거 없이 퍼진 통념)
- [Contested] 흔히 믿지만 근거가 약하거나 반증된 것들
```

> **Gottman 경고**: 김창준의 Gottman 사례에서 따온 이름. "친구 사귀기 전문가"의 프로토콜이 실제로는 역효과를 냈듯, 근거 없이 전문가 권위만으로 퍼진 통념을 명시적으로 플래그한다.

> ✓ Gate 2: 설명적 + 처방적 발견 각 2개 이상 + 근거 수준 태그 부여 + `[Strong]`/`[Moderate]` 항목의 원문 URL 확보 완료. 미충족 시 → 주제를 좁히거나 인접 분야 근거로 보충, URL 미확보 항목은 태그 하향.

### ▶ [3/7] 깊은 제약 수집 (Deep User Gate)

근거 지형(2단계)을 본 **다음에야** 사용자가 의미 있게 답할 수 있는 정보들을 수집한다. **분할 게이트의 뒤쪽** — "어떤 자원·제약·측정기준을 가지고 이 근거를 적용할 것인지".

수행 항목:
1. 0단계 mirror + 현재 상황 응답을 다시 확인 (중복 질문 금지)
2. 2단계 근거 지형에서 발견된 옵션들 중 사용자가 실제로 선택할 수 있는 게 무엇인지 좁힌다
3. **`AskUserQuestion`을 한 번에 하나씩** — 다음 영역에서 누락된 것부터 순서대로 질문 (Hard Rules #8 참조):
   - 가용 자원/도구 (이미 가진 것, 새로 도입 가능한 것)
   - 시간·비용·인지부하 제약
   - 성공/실패를 어떻게 측정할 것인가

표준 질문 패턴 (자원/제약 예시 — 이 호출 하나로 다 묻지 말고, 답변 확인 후 다음 영역이 필요하면 같은 패턴으로 이어서 호출):
```
AskUserQuestion(
  question: "근거에서 본 접근들 중 현재 자원으로 시도 가능한 게 어떤 거예요?",
  header: "가용 자원",
  multiSelect: true,
  options: [
    { label: "[2단계에서 본 옵션 A]", description: "필요 자원·시간" },
    { label: "[2단계에서 본 옵션 B]", description: "필요 자원·시간" },
    { label: "지금은 어렵지만 6개월 내 가능", description: "..." }
  ]
)
```

첫 답변이 애매하거나 후속 결정에 영향이 크면, 같은 영역 안에서 더 깊이 파고드는 질문을 추가로 1개 더 호출한다 (예: "가용 자원" 답변이 "앱 활용 가능"이면 → "어떤 종류의 앱을 선호하세요?" 후속 질문).

이 단계의 핵심: 4단계 전문가 토론과 5단계 구현 설계가 **추상론으로 흐르지 않게** 사용자의 실제 도구/자원 위에서 진행되도록.

> ✓ Gate 3: 가용 자원·제약·측정기준 중 최소 1개 영역 응답 수집. 미충족 시 → 영역을 좁혀 재질문.

### ▶ [4/7] 근거 기반 패널 토론

> ⚠️ 이 토론은 Claude가 연구 기록과 학습 데이터를 기반으로 시뮬레이션한 것입니다. 실제 전문가의 현재 견해와 다를 수 있으며, 이들이 실제로 한 발언이 아닙니다. 이 고지는 저장물(7단계)에도 그대로 포함되어야 한다 — Hard Rules #7 참조.

**근거 지형 위에서** 전문가 패널을 소환하여 토론한다.

#### 전문가 선정 (6인)

선정 기준 (**권위가 아닌 근거 기여도** 기준):
- 해당 분야에서 핵심 연구를 수행한 연구자 (최소 3인)
- 해당 근거를 실무에 적용한 실천가 (최소 1인)
- 다른 분야에서 교차 관점을 제공할 수 있는 전문가 (최소 1인)
- **Implementation 전문가** 또는 **비판적 관점** 보유자 (최소 1인)

`--experts` 플래그로 사용자 직접 지정 가능 (이 경우에도 근거 기반 토론 원칙은 유지).

**민감 주제 가드**: 주제가 정책·법률·정치·의료적 처치 결정처럼 실명 오귀속의 파장이 큰 경우 (예: 개발협력/ODA 정책, 공중보건 지침), 0단계에서 실명 인물 패널과 역할 아키타입 패널(예: "개발경제학자 A", "현장 실무자 B") 중 어느 쪽을 원하는지 한 문장으로 확인하고, 실명을 쓰더라도 각 전문가 첫 발언 앞에 "(시뮬레이션)" 표기를 짧게 병기한다.

#### 토론 구조

1. **전문가 소개**: 이름, 전문 분야, **핵심 연구 기여** (저서보다 연구 기여 우선)
2. **근거 기반 라운드**: 2단계에서 발견한 근거에 대해 각 전문가가 해석/확장/반박
3. **사용자 맥락 적용 라운드**: 이 근거가 사용자의 구체적 상황에서 어떻게 적용되는가
4. **교차 검증**: 전문가 간 의견 충돌 시 **어떤 근거에 기반한 의견인지** 명시하며 토론

#### 토론 규칙

- 모든 주장에 근거 수준 태그 필수: `[Strong]`, `[Moderate]`, `[Emerging]`, `[Expert]`, `[Contested]`
- 2단계에서 이미 URL을 확보한 근거를 인용할 때는 원문 링크를 함께 재언급 (새 근거를 이 단계에서 처음 꺼낼 경우도 동일하게 URL 확보 원칙 적용)
- `[Expert]` 수준의 의견은 반드시 "이것은 근거가 제한적이며, 제 경험에 기반한 의견입니다"를 명시
- 만장일치더라도 근거가 약하면 그 사실을 솔직하게 표기

> ✓ Gate 4: 전문가 6인 선정 + 4라운드 토론 완료 + 모든 주장에 근거 수준 태그 부여. 미충족 시 → 전문가 수를 3-4인으로 축소하되 교차 분야 1인 필수 포함.

### ▶ [5/7] 구현 설계 (Implementation Design)

Implementation Science 원칙을 적용하여 **실제로 작동하는 실행 계획**을 만든다 (`references/implementation-guide.md` 참조).

> "좋은 베스트프랙티스도 구현 방법이 잘못되면 실패한다" — 빌 게이츠 재단 탁월한 교사 프로젝트 실패 사례

출력 형식:
```markdown
## 구현 설계

### Core Practice (절대 바꾸면 안 되는 핵심)
- 이 원칙/방법의 효과를 만드는 최소한의 핵심 요소들

### Peripheral Practice (맥락에 맞게 변형 가능)
- 핵심 기능은 유지하되 형태는 자유롭게 적응 가능한 요소들

### 적응 설계 (Adaptation)
- 사용자의 구체적 맥락(직업, 환경, 도구, 습관)에 맞춘 구현 방법

### 이해관계자 고려
- 이 변화가 영향을 미치는 사람들

### 퍼실리테이션 포인트
- 혼자 하기 어려운 부분, 활용 가능한 도구/자원
```

> ✓ Gate 5: Core Practice 최소 2개 + Peripheral Practice 최소 2개 식별. 미충족 시 → 4단계 토론에서 합의된 핵심 원칙 기반으로 재구성.

---

### ▶ [6/7] 실천 실험 설계 (PBE Loop)

EBP(근거→실천)에서 PBE(실천→근거)로 이어지는 **선순환 구조**를 설계한다.

출력 형식:
```markdown
## 실천 실험

### 최소 실험 (Minimum Viable Experiment)
- 1-2주 안에 시도할 수 있는 가장 작은 실험
- 명확한 성공/실패 판단 기준
- 측정 방법 (주관적 체감 + 가능하면 객관적 지표)

### 관찰 포인트
- 실험하면서 주의 깊게 관찰할 것들

### 근거 축적 방법
- 실험 결과를 어떻게 기록할 것인가
- N회 반복 후 자신만의 Practice-Based Evidence 정리

### 반복 주기
- 언제 실험을 평가하고 조정할 것인가
```

> ✓ Gate 6: MVE 1개 이상 + 성공/실패 기준 명시 + 반복 주기 설정. 미충족 시 → 5단계 Core Practice 중 가장 작은 것으로 MVE 재설계.

---

### ▶ [7/7] 저장 (User Gate)

6단계 완료 후 사용자에게 저장 여부를 확인한다.

```
AskUserQuestion(
  question: "전체 토론을 어디에 저장할까요?",
  header: "저장 위치",
  options: [
    { label: "Obsidian (3.Resource/ebp/)", description: "'/obsidian-save' 등 옵시디언 저장 커맨드가 있으면 호출 — EBP_{주제}.md" },
    { label: "현재 디렉토리 .md 파일", description: "Write 도구로 EBP_{주제}.md 저장" },
    { label: "저장 안 함", description: "대화창 출력만 유지" }
  ]
)
```

**의존성 주의**: 이 스킬 패키지에는 `/obsidian-save` 같은 옵시디언 저장 커맨드가 포함되어 있지 않다 — 사용자 환경에 별도 설치된 경우에만 동작한다. "Obsidian" 선택 시 먼저 해당 커맨드/MCP 도구 사용 가능 여부를 확인하고, 없으면 자동으로 "현재 디렉토리 .md 파일" 저장으로 폴백하며 그 사실을 사용자에게 알린다 (조용히 실패하지 않는다).

**중요: 요약하지 말고 1~6단계 전문을 그대로 저장한다.** 임의 축약 금지. 4단계의 시뮬레이션 고지 문구도 저장물에 포함한다.

저장 시 메타데이터:
- 파일명: `EBP_{주제요약}.md`
- 태그: `ebp`, `전문가패널`, `#{관련학문분야1}`, `#{관련학문분야2}`
- 본문 상단: `> 생성일: [[{YYYY-MM-DD}]]` + `> ⚠️ 아래 전문가 발언은 시뮬레이션이며 실제 발언이 아닙니다.`

> ✓ Gate 7: 사용자 선택대로 저장 완료(폴백 발생 시 폴백 사실 안내 포함) + 경로 안내. 미충족 시 → 전체 내용을 코드블록으로 출력하여 수동 복사 가능하게.

## --quick 모드

`--quick` 플래그 사용 시 (Dispatch 표의 `Quick Flow (0→4→5→6→7)`와 동일한 사양):
- 0단계(Mirror) 유지 — Mirror 없이 토론은 위험
- 1-2단계(학문 지도 + 근거 지형) 생략
- 3단계는 0단계 응답을 그대로 사용 (추가 질문 없음, 별도 단계로 표시하지 않음)
- `▶ [0/4] Mirror → [1/4] 패널 토론 → [2/4] 구현 → [3/4] 실험 → [4/4] 저장` 순으로 재넘버링
- 토론 중 근거 수준 태그는 여전히 사용하되, 근거 지형(2단계)을 건너뛰므로 새로 인용하는 근거는 `[Internal Knowledge]` 태그와 함께 그 한계를 명시
- `[Expert]` 수준 의견에 대한 경고 유지

## 톤 & 스타일

- 각 전문가의 실제 어투와 사상을 최대한 반영
- 전문 용어는 영어 OK, 설명은 한국어
- **비판단적이고 호기심 어린 톤** — 근거가 약한 것을 "틀렸다"가 아니라 "아직 검증이 부족하다"로 표현
- 실용적: 토론으로 끝나지 않고 반드시 **구현 가능한 실험**으로 연결
- 정직: 근거가 없으면 없다고 솔직하게 말한다

**Good**:
> **Kahneman**: [Moderate] Stanovich의 연구에 따르면, 시스템 2의 개입은 인지 부하가 높을 때 현저히 감소합니다. 다만 이것은 근거가 제한적이며, 실험실 환경에서의 결과임을 고려해야 합니다.

**Bad**:
> **Kahneman**: 시스템 1과 시스템 2가 있는데요, 시스템 2를 잘 활용하면 더 좋은 의사결정을 할 수 있습니다!

## Hard Rules

1. **근거 수준 태그 필수** — 4단계 모든 주장에 5단계 태그 중 하나 부여
2. **권위 논증 금지** — "X가 말했다"만으로 근거 인정 불가, 근거 출처 별도 명시
3. **AskUserQuestion 사용 강제** — 0·3·7단계는 반드시 도구 호출로 진행 (텍스트로 묻지 않음). 단, 0단계의 Mirror는 텍스트로 먼저 합의 후 AskUserQuestion 1개 호출
4. **`[Expert]` 등급은 명시적 경고 동반** — "근거 제한적, 경험 기반" 문구 필수
5. **`[Strong]`/`[Moderate]` 태그는 원문 URL 동반 필수** — 저자·연도·저널뿐 아니라 WebFetch로 열어본 원문 링크를 함께 표기. URL을 확보하지 못했으면 태그를 `[Emerging]` 이하로 낮추거나 `(원문 미확인)`을 병기
6. **Gate 통과는 텍스트로 출력** — 내부적으로만 판단하고 넘어가지 않는다. 각 단계 끝에 `✓/✗ Gate [N]` 한 줄을 반드시 출력 (Dispatch 절 참조)
7. **시뮬레이션 고지 유지** — 4단계 도입부 경고 문구를 7단계 저장물에도 그대로 포함. 정책/법률/의료처럼 실명 오귀속 파장이 큰 주제는 4단계의 민감 주제 가드를 따른다
8. **질문은 한 번에 하나씩, 부족하면 후속 질문** — `AskUserQuestion` 호출 하나에는 질문(`questions` 배열 항목) 1개만 담는다. 여러 개를 한꺼번에 묻지 않는다. 답변을 받은 뒤에도 진행에 필요한 정보가 더 있으면 짐작하지 말고 후속 `AskUserQuestion`을 이어서 호출한다. 이 원칙은 0·3·7단계뿐 아니라 진행 중 정보 부족을 발견한 모든 단계에 적용된다 (예: 4단계에서 사용자 맥락 적용 라운드 중 애매한 지점 발견, 5단계 적응 설계 중 세부 제약 불명확 등)

## Edge Cases

| 시나리오 | 기대 동작 |
|---------|----------|
| 비학문적 주제 ("오늘 저녁 뭐 먹을까?") | 가장 가까운 응용 분야 탐색 (예: Food Science, Nutrition) |
| 극도로 좁은 니치 주제 | `[Expert]` 수준 의견이 주가 됨을 사전 고지, 인접 분야 유사 근거 활용 |
| 복수 주제 동시 요청 | 주제를 분리하여 하나씩 처리할 것을 제안 |
| 전문가 6인 구성 불가 (니치 분야) | 3-4인으로 축소, 교차 분야 1인 필수 포함 |
| WebSearch/WebFetch 사용 불가 환경 | 내부 지식으로 진행, 모든 근거에 `[Internal Knowledge]` 태그. WebSearch는 되지만 WebFetch만 불가하면 원문 미확인으로 태그 하향 |
| 옵시디언 저장 커맨드(`/obsidian-save` 등) 미설치 | "현재 디렉토리 .md 파일" 저장으로 자동 폴백 + 사용자에게 폴백 사실 안내 |
| 주제가 너무 넓음 ("건강") | 사용자에게 좁히기 질문 ("수면 건강? 심혈관 건강? 정신 건강?") |

## Checklist Before Stopping

- [ ] 0단계: Mirror 합의 + 현재 상황 `AskUserQuestion` 1개 응답 수집 + `✓ Gate 0` 출력
- [ ] 1단계: 학문 분야 2개 이상 + 주 근거원 선택 (0단계 응답 반영) + `✓ Gate 1` 출력
- [ ] 2단계: 설명적·처방적 발견 각 2개 이상 + 근거 수준 태그 + `[Strong]`/`[Moderate]` 항목 원문 URL 확보 + `✓ Gate 2` 출력
- [ ] 3단계: 자원·제약·측정기준 중 1+ 영역 `AskUserQuestion` 응답 수집 + `✓ Gate 3` 출력
- [ ] 4단계: 전문가 6인(또는 축소 구성) 선정 + 4라운드 토론 + 전 주장 태그 + 시뮬레이션 고지 유지 + `✓ Gate 4` 출력
- [ ] 5단계: Core Practice 2+ + Peripheral Practice 2+ + `✓ Gate 5` 출력
- [ ] 6단계: MVE 1개 + 성공/실패 기준 + 반복 주기 + `✓ Gate 6` 출력
- [ ] 7단계: `AskUserQuestion`으로 저장 위치 확인 + 사용자 선택대로 처리(외부 커맨드 미가용 시 폴백 안내) + 시뮬레이션 고지 포함 저장 + `✓ Gate 7` 출력
- [ ] 모든 주장에 근거 수준 태그 부여
- [ ] `[Expert]` 등급 의견에 경고 문구 동반
- [ ] `AskUserQuestion`을 호출당 질문 1개씩 사용했는지, 부족한 정보는 후속 질문으로 이어갔는지 확인
- [ ] `[Strong]`/`[Moderate]` 등급 근거에 원문 URL 동반 (미확보 시 태그 하향 처리했는지 확인)

## Examples

`examples/EBP_타이핑vs말하기속도비교.md` — 실제 산출물 예시 (속독 강사 직업 컨텍스트, Speech Science + HCI 도메인).

같은 입력 재현 절차:
```
/expert-panel 타이핑 vs 말하기 속도 비교
```
3단계 컨텍스트 질문에 "측정 방법 통일이 필요한 상황 / 기존 측정 도구 없음 / 본인 기준선 수립 목적"으로 응답하면 유사 결과 생성.
